# 30 — 虚拟模型端点

> 本篇定义工作流如何暴露为可选择的"模型":provider 注册、streamSimple 实现、事件流映射、占位工具、usage 处理。
> 前置阅读:00-总览(D13/D14/D15/D16/D17)。
> ⚠️ 依据用户确认:**`pi.registerVirtualModel` 在 v1.1.0 实际不可用**,一律用 `pi.registerProvider(name, ProviderConfig)` 实现(D13)。

## 1. Provider 注册

扩展工厂内(装载工作流成功后)为每个工作流注册一个 provider:

```ts
pi.registerProvider('pi-workflows', {
    name: 'Pi Workflows',
    baseUrl: 'http://pi-workflows.invalid', // 不会被访问;占位
    apiKey: 'not-needed',
    api: 'pi-agents-virtual', // 自定义 api 字符串(不匹配任何内置实现)
    models: flows.map((f) => ({
        id: f.name, // pi-workflows/<name>
        name: f.title,
        reasoning: true, // 世界书/思维链映射需要 thinking 通道
        input: ['text', 'image'], // 图片经 WakeContext 进入口节点(20 §9.3);本声明表示"可接受宿主附图",终点输出仍为纯文本 markdown
        cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
        contextWindow: 1_000_000, // 见 §6 上下文窗口语义
        maxTokens: 1_000_000,
    })),
    streamSimple: streamVirtualWorkflow, // §2
});
```

- 所有工作流共用一个 provider,`id` 区分;`streamSimple` 按 `model.id` 找到工作流定义。
- 注册时机:扩展工厂内(装载阶段)——pi 文档允许工厂内 registerProvider(queued until runner binds),`/model`、`--model`、settings 均可见。
- 工作流文件修改后:`/reload` 重新装载并重注册(同 name 覆盖);**不做**运行中热替换流。
- 装载失败的工作流不出现在 models 里;全部失败则不注册 provider。

## 2. streamSimple 契约

```ts
function streamVirtualWorkflow(
    model: Model<Api>, // model.id = 工作流名
    context: TranscriptContext, // 宿主会话的完整请求上下文
    options?: SimpleStreamOptions,
): AssistantMessageEventStream;
```

实现流程(分段续跑架构,§6):

1. **同步创建流**:`const stream = createAssistantMessageEventStream()`,异步任务立刻启动(GitLab Duo 示例同款模式)。
2. **标题请求改道**:system 消息含标题生成特征(§6.5)且配置了 `titleModel` → 直接委托真实模型,不唤醒工作流。
3. **续跑识别**:transcript 尾部是 toolResult 时,以其 `toolCallId` 查续跑注册表(§6.2);命中 → 继续 PendingRun 推段;未命中 → 明确错误流(服务重启丢失注册表,提示重新发起)。
4. **首调**:提取唤醒输入(40 §4)并组装 WakeArgs;push start(空 AssistantMessage,provider="pi-workflows",model=model.id,usage 全 0);异步驱动工作流引擎,NodeEvent 流经 FlowSegmenter 切段(§6.1)后推送。
5. **边界收口**:段以占位 toolCall 收尾时,本批已推段组装成 assistant 消息 push done(stopReason "toolUse")→ 宿主执行占位工具 → toolResult 回填 → 再次调用 streamSimple(回到步骤 3)。
6. **落定收口**:工作流 outcome 就绪 → 本批段(去 toolCall)组装最终消息,无 text 块时补 outcome.text,push done(stopReason "stop")。注册表按 run 精确清理。
7. **错误/中断**:引擎抛错/节点失败 → push error(usage 全 0)→ end(D17);`options.signal` 级联中断(D16),收尾 push aborted。

**必须遵守的宿主约定**(custom-provider.md 已核实):

- start 必须在内容事件之前;done/error 恰好一个、且只出现一次(续跑产生的每条消息都独立遵守)。
- `text_delta`/`thinking_delta` 之外,每个 `_end` 事件必须发(content 索引与 partial 状态保持一致)。
- toolcall 事件的 arguments 在 `toolcall_end` 前必须是合法完整 JSON。
- stopReason "toolUse" 是续跑请求;"stop" 表示工作流已落定(终点文本)。

## 3. 流映射(子会话 → 虚拟模型流,经 FlowSegmenter)

各子会话事件由 run-node 压缩成透传包(NodeEvent),经 FlowSegmenter 切成「虚拟消息段」(§6.1),再由 stream 层推送:

| NodeEvent                                   | 段内块                       | 说明                                           |
| ------------------------------------------- | ---------------------------- | ---------------------------------------------- |
| `node-start`(agent 节点)                    | 换段 + thinking 前缀(§3.2)   | fn 节点不产生段内容(状态行走 statusLines)      |
| assistant `thinking_delta`(任意节点/子代理) | 当前段 thinking 块           | 前缀标注来源:`【规划 #2】…`(§3.2)              |
| assistant `text_delta`(任意节点)            | 当前段 text 块               | outputVisible=false 的节点 → thinking 块(§3.1) |
| 子会话工具调用开始(`tool-call`)             | 关段 → 工具专属段(占位,§4)   | 工具段立即出段 = 边界(宿主将续跑)              |
| 子会话工具结果(`tool-result`)               | 状态行(下一段 thinking 开头) | `✓/✗ <tool>` 摘要(§3.3)                        |
| `node-text`(结果回补)                       | 忽略                         | 流式已承载;旧 M4 纠偏通道作废                  |

### 3.1 每段 = 一次「LLM 可见回合」

一段 = thinking(可选)+ text(可选)+ toolCall(可选)。段以 toolCall 收尾 → 宿主续跑;以 text 收尾 → 该回合的自然终点。

**输出可见性(§3.1,节点配置 `outputVisible`,缺省 true)**:

- **true(缺省)**:节点输出先按 text 流式(观感优先);收口时纠偏——
  工具边界批(toolUse 消息)的所有 text 块降为 thinking(边界后必有续跑,不可能是最终回答);
  落定批(stop 消息)里非终点节点的 text 降为 thinking,终点节点 text 保留(即最终回答)。
- **false**:该节点全部输出始终走 thinking(不流式 text);若它同时是工作流终点,
  直到输出彻底结束才由落定收口一次性产生最终 text 块(不逐字流出)。

终点 = 工作流 outcome(非流式期间猜测);`text-delta.isTerminal` 字段不再消费,
流式 text/thinking 的实时分块在收口消息层纠偏,与旧 M4「预估+纠偏」同源但仅作用于消息组装层。

### 3.2 内容前缀与节流

- thinking 前缀格式:`【<节点label或agent title> #<visit>】`;层级用 `>` 连接:`【实现 #1 > 代码搜索】`(subagent)与 `【实现 #1 > dev-loop #1 > 实现 #1】`(工作流引用的子工作流,subflow 层同样按节点前缀展开)。前缀在进入新"来源"时插入一次,不逐 delta 重复。
- 全局配置 `streamPrefixes: boolean`(缺省 true)可关前缀(纯流式观感)。
- 不做合并节流:pi 事件流本身轻量,直通转发;唯一裁剪点是占位工具参数超大时(§4.3)。

### 3.3 工具结果摘要

真实工具结果(成功)不重复进流;但在该占位 toolcall 之后追加一条 thinking 行:`✓ <tool> (<duration>ms, <结果字节摘要,如 "42 行输出">)`。失败:`✗ <tool>: <错误首行>`。让用户在折叠的思考流里看到工具成败,又不污染回答。

## 4. 占位工具(D14)

### 4.1 为什么要占位

虚拟模型 assistant 消息里出现 `toolCall` 块时,pi agent loop 会**真的执行**同名工具并把结果回填(这是 pi 的固定循环)。占位策略 = 注册与透传调用**同名**的空实现工具,返回固定文案。效果:

- 用户在 TUI/pi-web 看到工具调用卡片(真实参数+占位结果),有"工作流在干活"的过程感;
- 宿主模型收到的 tool result 是固定文案(「该调用已在工作流内部真实执行,无需再处理」),不会误以为需要自己跟进;
- 不会重复执行真实逻辑。

### 4.2 注册与命名

- 占位工具名:透传时对真实工具名做前缀化:`agents_<sanitized tool name>`(如 `agents_read`、`agents_comfyui_generate`)。**不直接用原名**,避免与宿主真实工具撞名(宿主同名工具会被占位定义覆盖或产生歧义)。
- 注册:扩展工厂里**动态注册不可行**(pi 工具不能注销,且 name 必须注册时确定)。采用**惰性固定集**:扩展启动时注册一个**固定名**占位工具 `agents_tool`,所有透传调用都映射到它,真实工具名/参数放 arguments 里:

```ts
pi.registerTool({
    name: 'agents_tool',
    label: '工作流工具调用(展示用)',
    description:
        '此工具由 pi-agents 工作流引擎调用,表示某个 Agent 在工作流内部真实执行了一次工具。返回值仅为占位说明。',
    parameters: Type.Object({
        agent: Type.String({ description: '执行该工具的 Agent/节点标注' }),
        tool: Type.String({ description: '真实工具名' }),
        arguments: Type.Record(Type.String(), Type.Unknown(), { description: '真实调用参数(原样展示)' }),
    }),
    execute: async (_id, params) => ({
        content: [{ type: 'text', text: '该工具已在工作流内部真实执行完毕;此结果仅为占位,无需处理。' }],
        details: { placeholder: true, tool: params.tool },
    }),
    // 活跃性由 setActiveTools 控制(§4.4):仅选中工作流模型时激活
    defaultActive: false,
});
```

- 透传时把真实调用包装成 `agents_tool` 的 arguments(真实名+参数原样内嵌);`toolcall_delta` 按组装好的 JSON 一次性推流(arguments 合法即可)。
- **权衡记录**:多一层包装牺牲了 TUI 上"看起来像直接调了 read"的还原度,换来注册机制简单可靠、不与宿主工具冲突。pi-web 渲染可读 arguments 还原细节。

### 4.3 超大参数

arguments(含内嵌参数)序列化 > 32 KiB 时截断为 `{truncated: true, bytes, preview}`(与 pi nestedCalls 的截断哲学一致),thinking 行注明"参数过大已截略"。

### 4.4 激活控制

- `model_select` 事件:新模型 provider 为 `pi-workflows` → `setActiveTools` 加入 `agents_tool`;切走 → 移除(保留宿主原有活跃集,先 `getActiveTools()` 快照再改)。
- 宿主在**未选中**工作流模型时恢复/分支到含占位调用的历史:占位工具已不在活跃集,agent loop 收到历史 toolCall 重放请求的概率为零(历史重放不触发执行),无影响;但**用户在同一宿主 session 切换模型后**,模型可能模仿历史再次调用 `agents_tool`——此时工具未激活,pi 返回"未知工具"错误,宿主模型自行收敛。可接受,文档标注。
- 会话恢复(resume):`session_start(reason=resume)` 时按该 session 分支上最近的 `model_change`(选中了哪个工作流)恢复激活状态(40 §9)。

## 5. 消息组装(每条虚拟消息)

```ts
{
    role: "assistant",
    content: [
        // 本批已推段的全部块,按实际发生序(思考→文本→工具→…):
        ...thinkingBlocks,   // 段内思考(来源前缀+状态行+摘要行)
        ...textBlocks,       // 各节点文本(终点文本 = 最后一条 text,20 §9.7 嵌图行在内)
        ...toolCallBlocks,   // 占位 agents_tool 调用(段尾;仅 toolUse 边界消息含)
    ],
    api: "pi-agents-virtual",
    provider: "pi-workflows",
    model: <workflow name>,
    usage: ZERO_USAGE,       // D15:全部 0,cost.total 0
    stopReason: "toolUse",   // 边界消息;落定消息恒 "stop"
    timestamp: Date.now(),
}
```

- **边界消息(stopReason "toolUse")**:content 含本批全部段(含占位 toolCall);宿主 agent loop 执行占位工具 → toolResult 回填 → 以续跑键(§6.2)再次调用 streamSimple。
- **落定消息(stopReason "stop")**:content 为末批段(剔除 toolCall——宿主已执行过,重复携带会诱导模型跟进;无 text 块时补 outcome.text 保证回答非空)。
- `reasoning: true` 声明(§1)使宿主允许 thinking 块存在;不需要 thinkingLevelMap(自定义 api 不消费)。

## 6. 分段续跑架构(M10)

整个工作流执行不再压成一条 assistant 消息,而是映射为**多轮虚拟消息**:每个子代理 LLM 轮 = 一条消息,占位 toolCall 驱动宿主 agent loop 续跑。

### 6.1 FlowSegmenter(切段)

`session/segmenter.ts`:NodeEvent 流 → `FlowSegment[]`(段 = thinking/text/toolCall 块序列 + endsWithToolCall 标记)。规则:

- `node-start`(agent 节点)→ 关旧段、设前缀(§3.2);fn 节点跳过(runner 已自行发状态行);
- thinking/text delta → 当前段对应块(前缀/状态行在首个 delta 前 flush 进 thinking 开头);
- `tool-call` → 关当前段,新段只装占位调用,**立即出段**(endsWithToolCall=true)——宿主在 tool-call 后即续跑,不等 tool-result;
- `tool-result` → 摘要行进状态行通道(下一段 thinking 开头),不持有段;
- 落定(`finish()`)→ 闭合尾部未收口段。

### 6.2 PendingRun 与续跑注册表

`session/stream.ts`:每个工作流运行 = 一个 PendingRun(segmenter/buffer/settled/finalText/error/registeredIds)。续跑注册表 `Map<toolCallId, PendingRun>`:

- 占位 toolCall id 全局唯一(`agents-<随机段>-<序号>`;进程重启不撞);
- 边界段产出的 toolCall id 注册进表;宿主把 id 原样写进 toolResult.toolCallId,续跑时凭它 O(1) 找回;
- 落定后按 run 精确清理(`registeredIds`),不影响其它并发运行;
- 注册表丢失(进程重启)→ 续跑请求得到明确错误流,用户重新发起即可。

### 6.3 段推送与收口

推段任务轮询 buffer(20ms):遇边界段或落定即收口本条消息。边界消息 content 含本批**全部**已推段(工具调用前的思考/文本都要进 transcript);落定消息 content 为末批段(去 toolCall)+ 必要时补终点文本。每条消息独立满足宿主约定(start 最先、done/error 恰一、`_start/_delta/_end` 配对)。

### 6.4 终点判别:无预估

终点 = 工作流 outcome,不是流式期间的猜测。中间节点文本保留为 text 块(与 pi 原生多块消息一致),终点段流式文本天然就是回答;仅当整轮无任何 text 块(纯 fn 工作流/快速完成)时补 outcome.text。旧 M4「终点预估+纠偏」通道作废,`text-delta.isTerminal` 字段不再消费。

### 6.5 标题生成请求改道(titleModel)

pi-web 的新会话标题生成(system 消息含「Generate a concise title for a coding-agent chat session」特征)会误触发完整工作流(×2 根因)。配置 `titleModel`(config: `"provider/id"`)后,识别该特征 → 委托真实模型完成标题;未配置 → 照旧走工作流(行为不变)。

### 6.6 防无限续跑

续跑链条由工作流自身收敛性保证(引擎 maxHops/节点路由有界);续跑键随落定清理,即使宿主模型异常再调 `agents_tool`(未注册 id)→ 明确错误流,不会复活已落定的工作流。

## 7. 上下文窗口语义

- 虚拟模型声明超大 contextWindow/maxTokens(§1),因为真实限制在子会话各自的物理模型上;宿主基于声明值做 compaction 判断,不该因虚拟值触发。
- 宿主对话历史会持续增长(每轮 = 用户消息 + 工作流巨长 assistant 消息)。**宿主侧膨胀控制**:
    - 占位 toolCall 块与 thinking 块都会占用宿主上下文。全局配置 `historyFootprint: "full" | "compact"`(缺省 "full"):
        - `full`:上述完整结构(过程感最大化)。
        - `compact`:历史重放时压缩——`message_end` 事件中检测**自己 provider** 的旧消息并替换为单行摘要文本块(「[工作流 dev-loop 第 N 轮:输出 …前 200 字…,工具调用 12 次]」),流式过程中的消息不受影响(message_end 只能改"刚完成"的消息,故 compact 模式改为在下次唤醒的引擎入口做一次**宿主历史改写**:`context` 事件把旧 assistant 巨消息替换成摘要;本扩展在自己会话里注册该钩子,详见 40 §10)。
    - 第一期先实现 `full` + 文档提示(用 `/compact` 手动收缩);`compact` 作为已设计、随实现排期的增强。

## 8. 与宿主消息转换的边界

- `getCurrentSystemPrompt`/`getCurrentTools` 用于确认请求形态;占位工具声明**不出现在子会话**(它只存在于宿主),透传与占位是两个方向,别混淆:
    - 子会话 → 宿主流:真实工具调用 → `agents_tool` 占位调用(§4)。
    - 宿主 → 子会话:宿主 system prompt(一般是 pi 默认提示词)不传给子会话;子会话有自己的 systemPrompt(Agent 定义)。
- 宿主用户消息中的图片:提取为 `wake.images` 进入口节点(20 §9.3);文本块中图片位置保留 `[图片 xN]` 占位。**不**向宿主返回任何图片块(AssistantMessage 无 image 块);终点图片以 markdown 相对路径行出现在文本块内(20 §9.7)。

## 9. 模型目录与选择

- `/model` 中显示:`pi-workflows / <workflow name>`(title 为显示名)。用户选中 → `model_change` 记录在该宿主 session 分支上。
- `--model pi-workflows/review-loop`、settings `defaultModel`、scopedModels 均自然可用(provider 机制免费获得)。
- 同名工作流被工作区覆盖后,`/reload` 重注册,选中状态按 id(= name)延续,无需用户重选。
- 虚拟模型**不可**作为 Agent/节点的 `model` 指定值(只解析物理模型,10 §3.1);工作流之间也不能用"选虚拟模型"的方式互相嵌套——组合走 subagent 工作流引用(10 §6.1)。

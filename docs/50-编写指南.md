# 50 — 编写指南(Agent 与工作流作者)

> 面向:想用 pi-agents 编排自己智能体的用户。字段规范以 10 / 20 为准,本篇讲**怎么写好**。
> 阅读顺序:先跑通 §1 的最小例子,再按需查其余小节。

## 1. 十分钟上手

### 1.1 目录(一条命令生成)

在 pi 里执行:

```
/agent-init              # 当前工作区:<cwd>/.pi/chlamydomonos-agents/
/agent-init --global     # 全局:~/.pi/agent/chlamydomonos-agents/
```

会创建 `agents/` `agent-flows/` `lorebooks/` 三个子目录,以及两个**为你写代码服务**的文件:

| 文件             | 作用                                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `tsconfig.json`  | 已配好 `moduleResolution: Bundler` / `strict` / `noEmit`,并把包名 `@chlamydomonos/pi-agents` 映射到下面的 shim                       |
| `pi-agents.d.ts` | 一行 `export * from '<...>/src/extension/types'`,把作者契约指向真实 `types.ts`。**无需安装本包**也能在编辑器里得到完整类型提示与报错 |

已有文件不会被覆盖(可放心重复执行;`tsconfig.json` 只在你手动删除后才会重写)。之后直接在该目录写 `.ts` 即可:

```
.pi/chlamydomonos-agents/          # 只对这个工作区生效
~/.pi/agent/chlamydomonos-agents/  # 全局可用(工作区同名者覆盖全局)
```

### 1.2 写一个 Agent

```ts
// .pi/chlamydomonos-agents/agents/notetaker.ts
import type { AgentDefinition } from '@chlamydomonos/pi-agents';

export default {
    name: 'notetaker',
    title: '会议纪要员',
    description: '把对话内容整理为结构化纪要',
    // 系统提示词建议用列表:一段角色,一段格式(可读性好;世界书 system 条目可插中间,10 §5.1)
    systemPrompt: ['你是会议纪要员。把用户给你的内容整理为:# 主题 / # 决议 / # 待办(带负责人)三段。不要评论内容本身。'],
    tools: [], // 纯文本任务,不需要工具
} satisfies AgentDefinition;
```

### 1.3 写一个单节点工作流并使用

```ts
// .pi/chlamydomonos-agents/agent-flows/notes.ts
import type { FlowDefinition } from '@chlamydomonos/pi-agents';

export default {
    name: 'notes',
    title: '纪要',
    description: '与纪要员对话',
    nodes: { main: { agent: 'notetaker', sessionMode: 'inherit' } },
    entry: 'main',
    edges: {},
} satisfies FlowDefinition;
```

重启 pi(或 `/reload`)→ `/model` 选 `pi-workflows / notes` → 直接对话。你说的每句话都会被整理成纪要。

## 2. Agent 编写要点

### 2.1 systemPrompt:人格与作业指导书(字符串或列表)

- 写清楚:角色、输入是什么形态、输出格式、边界(不该做什么)。字符串或字符串列表均可(列表 \n\n 连接);**复杂 Agent 建议列表**——世界书 system 条目可用 `slot` 精确插入两段之间(10 §5.1),如公司固定规范插槽 0、项目专属约束插槽 1。
- 工作流中上游传来的内容就是"输入形态"——如评审员会收到代码 diff 文本,systemPrompt 里就要写"你将收到代码改动文本"。
- 反例:"你是一个乐于助人的助手"——等于没写。

### 2.2 工具白名单:最小够用原则

- 给评审员 `bash` 就是让它能跑测试(有时是好事),也给它删文件的能力(通常不是你要的)。
- 白名单里写不存在的工具名不会报错(静默忽略),但说明你拼错了——用 `/agent-usage -v` 查"被跳过的白名单工具"。

### 2.3 世界书:什么时候用、用哪级

**选层级**(D20,合并优先 Agent > 工作流 > 工作区):

| 内容归属                   | 放哪                                |
| -------------------------- | ----------------------------------- |
| 所有 Agent 都要遵守的规范  | 工作区级 `lorebooks/*.ts`(自动生效) |
| 本工作流全部节点的流程约束 | FlowDefinition.lorebook             |
| 单个 Agent 的人格/领域知识 | Agent 定义的 lorebook               |

工作区级文件里用 `ctx.agent` 筛选(只给某些 Agent 注入),它自己没有"所属 Agent"。

**选注入目标**(条目 `target`):

- `target: "depth"`(缺省):随对话变的状态/每轮规则。适合:输出格式约定、随任务变化的状态(trigger 读文件)、循环轮次提醒(读 `ctx.flow.currentNode`/`trail`)。
- `target: "system"`:稳定的规则/知识,要出现在系统提示词里(某些 provider 对 system 前缀有缓存优势)。适合:风格规范、术语表、固定的安全约束;用 `slot` 控制插位。

不适合任何世界书的:

- 一次性任务说明 → 放进上游 pass 的文本。
- 很长的参考资料 → 直接写进 systemPrompt 列表(改它比世界书直白)。

**token 提醒**:非持久化 depth 条目**每次 LLM 请求都注入**(子会话内每次工具循环也重算);system 条目每请求重算进提示词。长条目 × 多轮循环 = 线性膨胀;稳定内容优先 system/列表,动态内容才走 depth。

### 2.4 sessionMode 怎么选(节点属性)

> sessionMode 是工作流节点的字段(20 §2.2),不在 Agent 定义里;下表帮助你在**节点上**做选择。

| 场景                               | 模式      | 理由                              |
| ---------------------------------- | --------- | --------------------------------- |
| 评审/总结类,每轮输入自包含         | `fresh`   | 上一轮记忆反而造成偏见;也省上下文 |
| 规划者,维护跨轮任务清单            | `inherit` | 需要记住"说到哪了"                |
| 长循环里被反复进入的实现者         | `inherit` | 记得自己上轮改了什么,避免重复劳动 |
| 输出敏感(不能被历史带偏)的终点节点 | `fresh`   | 输出只由本轮输入决定              |

inherit + 长对话会撞上下文上限(40 §3.2):子会话不会自动压缩,撞了就报错。长跑工作流要么给 inherit 节点的 Agent 写"自己维护便签"的自律提示,要么控制轮数(maxIterations)。

### 2.5 Subagent:委派什么

- 把**专业纵深**做成 subagent(搜索员、测试员、资料检索员),主 Agent 做编排。
- subagent 的 `description` 是主 Agent 选它的唯一依据——写成"什么时候该调用我"的说明书。
- 深度 ≥3 层会显著变慢且难调试;两层层级(编排者 → 执行者)是甜点区。
- **subagent 也可以指向一个工作流**(10 §6.1):想让某 Agent 拥有"多步骤流水线"能力(如"跑一遍 dev-loop")而不必手工编排时,把它做成工作流再引用。代价:阻塞、不可中途干预,引用图不能成环。

## 3. 工作流编写要点

### 3.1 从线性开始,再引入环

```
第一步:entry → B(终点)              # 验证 Agent 各自能干活
第二步:entry → B → C(终点)          # 验证 pass 文本能被 C 消化
第三步:B → C → route 回 B + maxIterations   # 引入环
```

每一步都用真实对话跑一遍再进下一步。环是最容易出错的部分,单独引入。

### 3.2 环的协议设计

让循环可持续的关键是**在输出里埋结构化信号**,route 靠它判断:

- 让评审 Agent 的 systemPrompt 规定:"通过时最后一行必须是 `LGTM`,否则列出问题"。route 正则匹配之。**信号必须可靠**(模型偶尔忘记 → route 里给缺省走向,别让缺省是"再循环一轮",那会烧满 maxIterations)。
- maxIterations 设为"人类可接受的浪费上限",不是"期望轮数"。期望 2 轮就设 4。
- 终点前放一个 fresh 的总结者 Agent,输出干净(20 §4)。

### 3.3 pass 的选择

| 需求                     | 写法                                                            |
| ------------------------ | --------------------------------------------------------------- |
| 直接把上游输出给下游     | 默认,不写 pass                                                  |
| 加上下文/轮次说明        | `{mode:"template", template:…}`                                 |
| 下游需要结构化数据做路由 | custom transform 返回 `{userMessage, data}`;route 读 `out.data` |
| 不想传内容(下游自查)     | `{mode:"none"}`(下游要自己有工具去读工作区)                     |

模板里引用上游 data:`{{data.round}}`;data 只在同一条边有意义,别跨边依赖。

### 3.4 何时用函数节点

确定性步骤别花钱:JSON 解析、格式转换、拼上下文、调用本地脚本,写 `run` 函数(20 §2.2),不走 LLM。

- 判断标准:**输入定了输出就定**的步骤 → 函数;需要理解/生成/决策 → Agent。
- `run` 里别做慢活长活(无超时保护,阻塞在它上面宿主只能 Esc);外部命令交给 Agent 节点用 bash 工具跑,反而有工具超时与可见性。
- route 读解析结果:`run` 返回 `{text, data}`,`route(out) => out.data.status === 'ok' ? 'done' : 'retry'`。
- 函数节点在 thinking 流里只有一行状态(`—— 函数节点 X ——`),没内容可看——调试靠 `/agent-usage -v`(耗时)与返回文本(它会进 trail,作为下个节点的输入可见)。

### 3.5 调试

1. **装载错误**:`/reload` 后注意启动 warning;`/agent-usage -v` 不显示就说明工作流没注册成功。
2. **route 没按预期走**:开 `streamPrefixes`,看 thinking 流里的 `—— 进入节点 X ——` 序列;或临时在 route 里 `console.log`(pi 运行日志可见)。
3. **输出不对**:先单独验证终点 Agent(给它同样的输入手动跑),再查 pass 文本。
4. **工具没执行**:确认 Agent 的 `tools` 白名单包含它;占位工具 `agents_tool` 的卡片里能看到真实工具名与参数(30 §4.2)。
5. **ask_user(向用户提问)**:pi-web 提供的提问表单工具,工作流 Agent 可以真实使用——把 `ask_user` 加进 `tools` 白名单,Agent 调用后问题会以浏览器表单呈现给用户,回答(含未回答的题)作为后续消息唤醒工作流。约束:①仅在 pi-web 宿主下可用(CLI 无此工具);②Agent 调用 `ask_user` 后**该次唤醒的工作流在此挂起**(提前落定,后续节点不执行;回答触发的是一次全新唤醒);③它终止单轮,不能在提问的同一轮里继续追问。
6. **想看子会话真实对话**:第一期无导出功能;用 `/agent-usage -v` 的调用计数/耗时做健康度判断(二期考虑落盘子会话日志)。

### 3.6 token 经济

- 每个节点的输入 = pass 文本 + 世界书条目 + (inherit 时的历史)。给中间节点"读文件拿材料"(工具)而不是"在 pass 里塞材料"(文本),往往更省。
- 占位工具在宿主上下文里也占 token(30 §6);重工作流建议定期 `/compact` 或等 compact 模式(二期)。
- `/agent-usage` 看真实消耗;虚拟模型在 `/session` 里显示 0 是**正常的**(D15,防重复计费)。

## 4. 配方

### 4.1 评审循环(带轮次与总结)

见 20 §8 示例(dev-loop)。要点:评审员 fresh、实现者 inherit、总结者 fresh、maxIterations=4、LGTM 信号。

### 4.2 多专家串联再汇总

```ts
nodes: { arch: {agent:"architect"}, security: {agent:"sec-reviewer"}, merge: {agent:"synthesizer"} }
edges: { arch: "security", security: { route: () => "merge" } }
// security 的 pass:template 把两段意见都带上?不行——pass 只看直接上游。
```

**多上游意见传递**:pass 只能拿直接上游输出。要汇总 arch 与 security,把 arch 的产出经 data/scratch 传:`security` 的 transform 把 `ctx.scratch.arch = out.text` 存下,`merge` 的 transform 读 scratch 拼接(20 §PassContext.scratch 与 route 共享)。scratch 是唤醒内全局便签,跨节点传大块内容的正道。

### 4.3 带工具的研究员(单节点 + subagent)

```ts
// researcher.ts: tools:["web-search","read"], subagents:["librarian"]
// solo-research.ts: nodes:{main:{agent:"researcher", sessionMode:"inherit"}}, edges:{}
```

用户与 researcher 多轮对话;它自己派 librarian 查资料。所有工具调用以占位卡片实时可见。

### 4.4 图片工作流(pi-comfyui 生成 → 看图评审 → 嵌图)

完整示例见 20 §9.9。要点:

- **分工**:生成(带 `comfyui_generate` 工具的 Agent 落盘)→ 收集(函数节点 `ctx.files.list` + `readImage` 读图,images 通道)→ 评审(Agent,模型需支持 image 输入)→ 终点。
- **接力靠 pass**:`review` → `polish` 边写 `{mode:'text', images:'forward'}` 才转发;不写 = 图到评审为止,终点不嵌图。
- **终点自动嵌图**(D22,缺省开):终点产出的图片在最终回答末尾追加 `![工作流图片](comfyui-output/xxx.png)`;pi-web 聊天直接渲染(懒加载、点击放大);TUI 里是普通文本行(非目标)。`embedFinalImages: 'off'` 可关。
- **Agent 不产图**(20 §9.6):最终 assistant 消息没有图片块,想让图进流必须经函数节点读取;Agent 在文本里写 `![…](路径)` markdown 也能显示(同一渲染机制),但没有"自动附加"的可靠性保证。
- **上限**:唤醒附图 ≤4、单图 ≤2MiB、单节点产出 ≤8(40 §11);超限函数节点直接 error 流,看 warning 修代码。

### 4.5 让面板图更好看(targets 声明)

条件边加 `targets: ['done', 'writer']`(20 §3.1),pi-web 运行图就能画候选分支虚线;不写也有 `?` 标记兜底。纯展示,不影响执行——**顺手声明,调试时一目了然**。

### 4.4 世界书动态状态与工作区规范

```ts
// Agent 级:动态状态(depth 条目)
lorebook: {
    trigger: async (ctx) => {
        const spec = await fs.readFile(".pi/review-standard.md", "utf8");
        return [{ depth: 0, content: `当前评审标准:\n${spec}` }];
    },
}
```

标准文件改了,下一次请求自动生效(非持久化)。

```ts
// lorebooks/house-style.ts:工作区级,自动对全部子会话生效;用 ctx.agent 筛选(D20)
export default {
    entries: (ctx) =>
        ctx.agent.startsWith('coder') || ctx.agent.startsWith('reviewer')
            ? [{ target: 'system', slot: 0, content: '本仓库规范:缩进 4 空格;错误必须带上下文前缀。' }]
            : [],
};
```

system 条目插在每个相关 Agent 系统提示词的最前面(slot 0),depth 条目每轮注入的总量就小了。

## 5. 常见错误速查

| 现象                          | 原因与处理                                                     |
| ----------------------------- | -------------------------------------------------------------- |
| `/model` 里没有我的工作流     | 装载失败(看启动 warning);或 name 与全局某文件冲突被覆盖        |
| "agent not found: xxx"        | nodes[].agent 拼错,或该 Agent 文件装载失败                     |
| 工作流跑几轮就结束且无总结    | maxIterations 触发(终点=最近完成节点);调大或修 route 信号      |
| 一直循环到 maxHops 报错       | route 永不返回 done 且没配 maxIterations(40 §4.3)              |
| 子会话报上下文超限            | inherit 节点历史过长;改 fresh / 减轮数 / 让 Agent 自律摘要     |
| 占位工具显示"未知工具"        | 模型切换后宿主模型模仿历史调用;无害,自动收敛(30 §4.4)          |
| 世界书条目没出现              | trigger 抛错(按无注入继续,查日志);或 persistent 模式下已注入过 |
| Esc 后再对话,inherit 节点失忆 | 设计行为:中断后弃池(40 §8),下次首唤醒重新导入宿主历史          |
